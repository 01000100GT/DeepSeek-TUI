## 一、架构全景

### 1.1 顶层结构：14 个 workspace crate

                  ┌──────────────┐

    deepseek-tui    one-shot      serve/doctor
    (crates/tui)    (HTTP API)    (管理命令)
           │

    ┌──────────────────────────────────────┐
    │          Core Engine                  │
    │  (crates/tui/src/core/engine.rs)     │
    │                                      │
    │  engine ─▶ session ─▶ turn_loop      │

### 1.2 14 个 crate 的职责分工

| Crate | 职责 | 状态 |
|-------|------|------|
| `cli` | CLI 参数解析 (clap)，命令路由，`deepseek` 调度器 | 稳定，薄层 |
| `tui` | **仍为事实主运行时**：引擎、TUI、工具实现、LLM 客户端、会话持久化 | 架构迁移进行中 |
| `core` | 重新提取的 Runtime / ThreadManager / JobManager | 新 crate，正在接替 tui 的核心职责 |
| `agent` | ModelRegistry：模型 ID → Provider 解析 | 已独立 |
| `config` | 配置加载、Profile、环境变量优先级 | 已独立 |
| `tools` | ToolRegistry / ToolCall / ToolHandler trait 定义 | 已独立 |
| `protocol` | 请求/响应帧类型、EventFrame、ToolPayload | 已独立 |
| `mcp` | MCP 客户端 + stdio 服务端 | 已独立 |
| `state` | SQLite 线程/会话持久化 | 已独立 |
| `execpolicy` | 审批/沙箱策略引擎 | 已独立 |
| `hooks` | 生命周期钩子（stdout / jsonl / webhook） | 已独立 |
| `secrets` | OS keyring API 密钥存储 | 已独立 |

> **关键事实**：架构文档（`docs/ARCHITECTURE.md`）明确声明 `crates/tui` 仍然是"活着的终端用户运行时"——拆分是增量进行的，尚未完成。多个已独立 crate（`app-server`、`tui-core`）目前仍为骨架状态，实际逻辑仍在 `tui` 中。

### 1.3 数据流：一次完整的 Turn

```
用户输入 (TUI)
    │
    ▼
Op::SendMessage ──▶ Engine::handle_send_message()
    │
    ├─ 1. pre_turn_snapshot()     ← side-git 快照
    ├─ 2. session.add_message()   ← 用户消息入会话
    ├─ 3. refresh_system_prompt() ← 按模式/上下文刷新系统提示词
    ├─ 4. build_tool_registry()   ← 注册所有工具 + MCP 工具
    │
    ▼
handle_deepseek_turn() ← 核心 turn 循环
    │
    ├─ while steps < max_steps:
    │   ├─ layered_context_checkpoint()  ← 软缝 (seam) 压缩
    │   ├─ compact (if needed)           ← 容量守卫
    │   ├─ LLM API call → stream         ← DeepSeek Chat Completions
    │   ├─ parse tool_calls from delta   ← 工具调用解析
    │   ├─ for each tool_call:
    │   │   ├─ exec_policy.check()       ← 策略审批
    │   │   ├─ approval modal (if needed)← 用户审批
    │   │   ├─ tool_registry.dispatch()  ← 工具执行
    │   │   ├─ lsp_hooks (if edit file)  ← LSP 诊断注入
    │   │   └─ append result to messages
    │   └─ check subagent completions    ← 子代理完成哨兵
    │
    ├─ maybe_advance_cycle()             ← 检查点-重启周期
    └─ TurnComplete event                ← 通知 UI
```

### 1.4 核心子系统

**会话持久化体系**（三重保障）：

```
~/.deepseek/
├── sessions/              ← SQLite 会话历史
├── sessions/checkpoints/  ← 崩溃恢复检查点 (latest.json)
├── snapshots/<hash>/.git  ← side-git 每轮快照 (/restore N 回滚)
└── tasks/                 ← 持久化任务队列、时间线、产物
```

**上下文管理策略**（多层防御）：

- **L1 软缝 (Seam)**：FLASH 模型生成 `<archived_context>` 导航块，appended 而非删除消息
- **L2 压缩 (Compaction)**：自动/手动 token 阈值触发，汇总旧消息
- **L3 周期 (Cycle)**：检查点-重启架构，完全替换消息数组 + 摘要
- **紧急压缩**：容量守卫在接近模型限制时强制回收

**子代理系统**：

```
agent_spawn() ─▶ SubAgentRuntime (独立 session)
    │
    ├─ fork_context: true → 继承父系统提示词 + 消息 + 结构化状态
    ├─ 独立模型选择 (auto mode 路由)
    ├─ 独立思考级别
    ├─ 完成哨兵 → parent turn loop 注入 <deepseek:subagent.done>
    └─ 递归深度限制 (默认 3)
```

## 二、多领域专家团队评审

### 🌏 东方哲学视角

#### 2.1 阴阳失衡：热路径与冷路径的张力

系统在"快"（流式响应、实时渲染）与"稳"（持久化检查点、side-git 快照、崩溃恢复）之间大量投入。但二者并未形成良性循环——每次 turn 都同时做 `pre_turn_snapshot` + `post_turn_snapshot`，无论是否需要。这就像太极图中阴阳互生的动态平衡被打破，变成了僵硬的"两边都做"。

**具体表现**：

```rust
// crates/tui/src/core/engine.rs — handle_send_message()
// 每次发送消息都无条件执行 pre + post snapshot
if self.config.snapshots_enabled {
    let _ = tokio::task::spawn_blocking(move || 
        pre_turn_snapshot(&pre_workspace, pre_seq)
    ).await;
}
// ... 整个 turn 循环 ...
if self.config.snapshots_enabled {
    crate::utils::spawn_blocking_supervised("post-turn-snapshot", move || {
        post_turn_snapshot(&post_workspace, post_seq);
    });
}
```

> **建议**：引入"风险自适应快照"——仅在与上次快照有实质文件差异时才创建新快照。`pre_turn_snapshot` 可通过 `git diff --stat` 预判是否有必要。

#### 2.2 道法自然 vs 过度设计

14 个 crate 的模块化目标是正确的，但 `crates/tui/src/` 内部仍包含 50+ 个源文件——engine、TUI、工具实现、LLM 客户端、会话管理全部混杂在一个 crate 下。这违背了"无为"原则：拆分应该自然发生，而非强行规划。

14 个 crate 中有多个（`app-server`、`tui-core`）目前仍是骨架状态，实际逻辑还在 `tui` 中。这说明拆分节奏与实际需求脱节——先定义了接口和 crate 边界，再试图把代码塞进去，而非让代码自然生长出边界。

> **建议**：暂停新 crate 的创建，集中精力完成 tui → core 的迁移。每迁移完成一个子系统（如 `runtime_api.rs` → `app-server`），再考虑下一个。

#### 2.3 无为而治：auto-compaction 的失位

`auto_compact` 默认关闭（自 v0.6.6 起），理由是 checkpoint-restart cycle 替代了它。但 cycle 只在高 token 阈值触发，中间地带（60%-80% context 使用率）没有任何自动化干预。

系统提示词告诉模型"在 60% 时建议 compaction"，但 60% 没有任何机制触发。这是"放任不管"而非"无为而治"——真正的问题被交给模型去"建议"，而模型可能永远不提。

> **建议**：在 60% 阈值绑一个软性 notification（非 blocking），80% 触发 cycle。不给用户一个"一切正常"的假象。

### 🤖 AI 专家视角

#### 2.4 Thinking Token 污染：成本核算的根本性缺陷

自述的 bug："Token counting and cost estimation may be inflated due to thinking token accounting bugs"。这意味着每个 turn 的成本报告不可信。在一个成本敏感的产品中（Pro 模型 $0.87/1M output tokens），这是严重的信任问题。

**深层问题**：thinking tokens 在每次 API 请求中必须完整重放（否则 HTTP 400），但它们对模型的推理价值递减。系统没有区分"必须重放的 reasoning_content"和"仅为了 API 兼容性而重放的 reasoning_content"。

**具体链路**：

```
Turn 1: 用户提问 → 模型输出 thinking (3000 tokens) + 回答
Turn 2: 必须重放 Turn 1 的完整 thinking (3000 tokens) + 新的 thinking
Turn 3: 重放 Turn 1 + Turn 2 的 thinking (6000+ tokens) ...
```

> **建议**：实现 `reasoning_content` 的去重和摘要策略。对于 N 轮前的 thinking block，用一个简短的"历史推理摘要"替代完整重放。API 兼容性可通过保留最后一个 tool-call-bearing 消息的完整 reasoning 来满足。

#### 2.5 Prefix-Cache 自我矛盾

系统提示词强调"append, don't reorder"以保持 prefix-cache 命中率（约 90% 成本折扣）。但同时：

- **Cycle 机制**直接替换整个消息数组（cache 全量 miss）
- **Compaction** 重排消息顺序
- **LSP 诊断**作为 synthetic user message 注入，打破序列连续性
- **Seam 管理**在消息中间插入 assistant message

每次 cycle advance 都是一次完整的 cache invalidation，但代价模型中未体现。用户看到的成本不包括这笔"隐性税"。

#### 2.6 "Mismanaged Genius" 问题的根源

系统提示词自 v0.8.6 承认了这个问题：提示词是为低能力模型写的，没有充分鼓励子代理和并行执行。但修复更多是在提示词层面——在 `AGENTS.md` 和 session 提示词中加入了更强的并行指令，而非在引擎层面提供更好的原语。

**真正需要的是**：

- 引擎主动检测"连续 3 个 turn 没有 spawn sub-agent 且 context > 50%"，发出警告
- 为常见的并行模式（读 3 文件 + 搜 2 模式）提供组合工具
- 在工具调用返回后，引擎检查是否有其他可并行的工具调用被阻塞，自动建议并行化

#### 2.7 子代理完成哨兵的设计风险

```rust
tx_subagent_completion: mpsc::UnboundedSender<SubAgentCompletion>,
```

使用 unbounded channel 接收子代理完成事件。如果父 turn 循环暂时不消费（例如正在等待 LLM 响应），子代理完成事件会无限堆积在内存中。在极端情况下（同时 spawn 100+ 子代理，每个快速完成），可能导致内存压力。

> **建议**：使用 bounded channel 或为 unbounded channel 设置高水位告警。

### 🏗️ 软件架构师视角

#### 2.8 单体 TUI Crate 的持续膨胀

源代码行数估算（基于文件结构分析）：

| 文件 | 估算行数 | 问题 |
|------|----------|------|
| `crates/tui/src/core/engine.rs` | ~2000+ | 引擎逻辑 + 压缩 + RLM + cycle + seam + 子代理 |
| `crates/tui/src/main.rs` | ~5000+ | CLI 定义 + panic hook + shell 补全 + eval + 模板 + session + one-shot + MCP |
| `crates/tui/src/tools/` | ~40 文件 | 所有工具实现混杂在一个目录下 |

`main.rs` 同时包含 CLI 定义、panic hook、shell 补全、eval harness、模板生成、session 恢复、one-shot 执行、MCP 命令路由——严重违反单一职责原则。

> **建议**：`main.rs` 应立即拆分为：
> - `cli.rs` — 纯 CLI 参数定义
> - `commands/` — 每个子命令一个文件
> - `panic_hook.rs` — panic 处理独立

#### 2.9 双重状态存储的同步问题

会话状态同时存在两个地方：

- **内存**：`Session.messages: Vec<Message>` + `EngineConfig` 的各种字段
- **磁盘**：`StateStore` (SQLite) 中的 thread metadata + messages

二者通过 `emit_session_updated()` 和 `touch_message()` 手动同步，没有事务保证。崩溃可能导致内存状态与持久化状态不一致。

**示例风险场景**：

1. 用户发送消息 → `touch_message()` 写入 SQLite
2. 引擎开始 LLM 调用 → 收到 streaming 响应
3. 在写入 assistant 消息到 SQLite 之前崩溃
4. 恢复时：用户消息存在，assistant 响应丢失，但用户看到了部分响应

> **建议**：引入 write-ahead log (WAL) 或至少将 `touch_message` + 后续的 assistant 消息写入包裹在一个 SQLite 事务中。

#### 2.10 异步运行时的生命周期管理

`tokio::main` + `tokio::spawn` 广泛使用，但缺少结构化的并发管理。引擎内的 `FuturesUnordered` 用于并行工具执行，但取消传播依赖 `CancellationToken` 手动传递——没有使用 `tokio::select!` 或 structured concurrency 的 `JoinSet`。

```rust
// 引擎中多个 spawn 点没有使用 JoinSet 管理生命周期
spawn_supervised("subagent-mailbox-drainer", ..., async move { ... });
spawn_supervised("engine-event-loop", ..., async move { ... });
```

> **建议**：将关联的 spawn 任务纳入 `JoinSet`，在 shutdown 时统一等待并收集错误。

#### 2.11 测试覆盖率

仅在 `crates/agent` 中看到模块级测试（`model_registry` 的别名解析）。核心引擎、工具调度、TUI 渲染、LLM 流解析——没有发现对应的测试模块。

这是一个高风险信号。在没有测试的情况下修改 engine.rs 的任何部分都可能导致静默回归。

### 📐 算法专家视角

#### 2.12 Job Retry Backoff 缺少 Jitter

```rust
fn deterministic_backoff_ms(retry: &JobRetryMetadata) -> u64 {
    let exponent = retry.attempt.saturating_sub(1).min(20);
    let multiplier = 1u64.checked_shl(exponent).unwrap_or(u64::MAX);
    retry.backoff_base_ms.saturating_mul(multiplier)
}
```

这是纯指数退避，没有随机抖动（jitter）。在高并发任务失败时，所有重试会精确同步，造成雷鸣兽群效应（thundering herd）。API 限流场景下尤为致命。

> **修复**：加入 `+ rand::thread_rng().gen_range(0..backoff_ms / 2)` 的 jitter 项。

#### 2.13 Tool Dispatch 并行策略过于简单

```rust
if configured.supports_parallel_tool_calls {
    let _guard = self.runtime.parallel_execution.read().await;
} else {
    let _guard = self.runtime.parallel_execution.write().await;
}
```

这是一个全局的 RwLock——任何标记为 `supports_parallel_tool_calls=false` 的工具会排斥所有其他工具。但实际上，不安全的工具（如 `write_file`）只需要排斥其他写操作，读操作完全可以并行。

> **建议**：引入更细粒度的锁：
> - filesystem-write 排斥 filesystem-write
> - 允许多个 read 并行
> - shell-exec 使用独立锁

#### 2.14 Context Compaction 的 Token 估算

`estimate_input_tokens_conservative()` 是一个估算函数，用于决定是否触发压缩。但其精度直接影响两个关键决策：

1. 是否发送 API 请求（估算错误 → 400 error → 用户体验极差）
2. 是否触发紧急压缩（估算过高 → 过早压缩 → 丢失上下文）

估算精度没有在代码中量化记录。DeepSeek 的 tokenizer 与 OpenAI 不同，用 4 chars/token 的粗略估算在中文场景下可能严重偏离（中文每个字约 1.5-2 tokens，而英文约 0.25-0.3 words/token）。

> **建议**：使用 DeepSeek 官方 tokenizer 或至少针对 CJK 字符做特殊系数校正。在 `estimate_input_tokens_conservative()` 中加入语言检测逻辑。

#### 2.15 Capacity Controller 的阈值设定

`CapacityController` 使用固定的 token 阈值触发不同的守卫动作（RiskBand）。但 V4 模型有 1M context window，而实际有效窗口受 prefix-cache 命中率影响。当前的线性阈值模型无法反映"缓存命中的 token 成本是未命中的 1/100"这一经济现实。

> **建议**：引入"有效成本上下文长度"概念——将 cache-hit token 按折扣率折算后计算实际成本，基于此触发压缩/周期。

### 🎯 产品经理视角

#### 2.16 安装路径的维护负担

6 种安装方式（npm / Cargo / Homebrew / Docker / direct download / Scoop）加上 China mirror 特化路径。每个 release 需要：

- npm publish
- crates.io publish（2 个 crate）
- Homebrew formula 更新
- Docker image build + push
- GitHub Release 构建 5 平台 × 2 架构 = 10 个 binary
- Scoop manifest 更新

这是 6+ 条独立的分发渠道，每条的失败模式不同（npm 下载失败可恢复，但 hash 不匹配不可恢复）。

> **建议**：将 Homebrew 和 Scoop 的更新纳入 CI/CD 自动流程。同时在 README 中建议"大多数用户用 npm，高级用户用 Cargo"，减少选择焦虑。

#### 2.17 技能系统的鸡与蛋问题

技能系统很强大（composable skill packs from GitHub），但：

- 用户需要先知道"什么是 skill"才能开始使用
- 社区贡献的 skill 需要 discoverability（没有 marketplace / registry）
- `load_skill` 工具对模型来说是一个需要主动选择的负担

当前依赖模型从 system prompt 中的 skill 列表"自选"——但即使是最聪明的模型也可能不会总是选择正确的 skill。

> **建议**：加入一个轻量级的"提示技能"系统——当用户消息匹配某技能的 description 关键字时，TUI 在发送给模型前自动 prepend "💡 你可能想用 `/skill X`"。

#### 2.18 定位模糊

项目同时是：

- DeepSeek API 的终端客户端
- 一个 coding agent（类似 Claude Code）
- 一个 MCP 主机
- 一个 runtime API server
- 一个 sub-agent orchestrator

但这些角色的优先级没有在主文档中明确定义。README 以 "Terminal coding agent" 开头，但功能列表的 1/3 与 coding 无关（MCP server、HTTP API、user memory）。对于新用户，这是一张过于复杂的菜单。

> **建议**：在 README 开头加入一个"三句话定位"，明确回答：
> 1. 这是什么？（终端 AI 编程助手）
> 2. 为什么选它？（1M context + 极低成本 + DeepSeek V4 原生支持）
> 3. 什么时候用它？（日常编码、代码审查、架构设计、自动化任务）

#### 2.19 竞品差异化的表述不足

与 Cursor / Copilot / Claude Code 的关键差异：

| 能力 | DeepSeek TUI | Claude Code | Cursor |
|------|-------------|-------------|--------|
| Context 窗口 | **1M tokens** | 200K | ~128K |
| Input 成本 (cache miss) | **$0.14/1M** (Flash) | $3/1M | N/A (订阅制) |
| Input 成本 (cache hit) | **$0.0028/1M** (90% 折扣) | N/A | N/A |
| Thinking 可见性 | **实时流式展示** | 黑盒 | 黑盒 |
| 子代理 | 独立 session，并行 | 有 | 无 |
| MCP | 原生支持 | 有 | 部分 |

这些是真正的差异化优势，但在 README 中没有被突出强调。用户读完后对"为什么选 DeepSeek TUI 而不是 Claude Code"没有清晰答案。
